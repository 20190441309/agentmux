# 协调者 / 自动委派 · 设计

日期：2026-10-25
状态：草案，待评审
承接：设计文档 §2 非目标"agent 间自动委派路由"；README Roadmap

## 1. 目标

让用户用一句话描述任务，由系统把工作拆成若干子任务并分发给共享工作区里的不同 Agent，最后汇总。**用户始终在环中**：拆分方案必须经批准才会执行。

核心原则：
- 编排逻辑属于 daemon，不属于某个 Agent；任何 Agent 都可以作为"提议者"。
- 复用已有机制：共享工作区、`.agentmux/` 黑板、overlap 提示、手动接力，不另建一套通道。
- 默认保守：不批准就不执行；不自动合并冲突；不自动选择高成本动作。

## 2. 非目标（本期）

- 全自动、无人值守的多轮循环。
- 跨工作区委派。
- 基于模型的自动选择 Agent（先用用户指定或简单规则）。
- 文件锁（沿用 overlap 通知）。

## 3. 概念

- **Plan**：一次委派的整体，含目标描述、状态、若干 Task。
- **Task**：`{ id, title, prompt, assignee_session, depends_on[], scope_paths[], state }`。`scope_paths` 声明预期修改的路径，用于分区并行并与 overlap 检测联动。
- **Plan 状态**：`Proposed → Approved → Running → Done | Failed | Cancelled`。
- **Task 状态**：`Pending → Ready → Running → Done | Failed | Skipped`。

## 4. 流程（最小版本）

1. 用户在工作区内执行 `/delegate <目标>`，并选择一个"提议者"会话（默认当前会话）。
2. daemon 向提议者发送固定格式提示，要求返回结构化 JSON 方案（任务列表、依赖、范围、建议分配）。解析失败则展示原文并让用户重试，**不做猜测性修复**。
3. TUI 展示方案审阅界面：可编辑标题/提示词、改派 Agent、删除任务；校验依赖无环、`scope_paths` 重叠时给出警告。
4. 用户批准后，daemon 把无依赖任务置为 Ready 并派发给对应会话（沿用 `session/prompt`，并注入共享上下文前言与任务说明）。
5. 任务完成（该会话本轮结束且无错误）后，依赖它的任务变为 Ready；每个任务的结果摘要写入 `.agentmux/plan.md`，所有参与 Agent 的前言都会引用它。
6. 所有任务结束后，生成汇总（各任务摘要 + 变更文件列表 + overlap 记录），用户决定是否结束。

## 5. 失败与安全边界

- 任务失败：暂停依赖它的任务，通知用户，由用户选择 重试 / 改派 / 跳过 / 取消整个 Plan。
- 权限请求照旧进入权限收件箱，不因委派而自动放行。
- 会话被杀或 daemon 重启：Plan 与 Task 状态持久化；重启后进入 `Paused`，需用户确认继续（避免重复执行已发出的提示）。
- 每个任务只派发一次；用幂等键防止重放。
- 原生托管（PTY）会话没有结构化事件，**不能**作为被委派对象（无法判定完成），在方案审阅中置灰并说明原因。

## 6. 数据与接口

- 新增 `plans`、`plan_tasks` 表，复用现有迁移方式；事件新增 `PlanUpdated`、`TaskUpdated`。
- RPC：`plan/propose`、`plan/get`、`plan/approve`、`plan/cancel`、`plan/task_action`（retry/skip/reassign）。
- 黑板：`.agentmux/plan.md` 由 daemon 维护，Agent 只读。
- 依赖适配器能力清单（见 [能力清单设计](2026-10-25-adapter-capabilities-design.md)）判断某会话是否可被委派。**因此本设计的实现排在能力清单之后。**

## 7. 测试

- 纯逻辑单测：依赖图校验、状态机转移、就绪判定。
- mock-agent 端到端：提议 → 批准 → 并行执行 → 汇总；失败分支；重启恢复。
- PTY 回归：审阅界面在窄屏可操作，不依赖快捷键记忆。

## 8. 分步交付

1. 数据模型 + 状态机 + 持久化（无 UI）。
2. 提议与解析（`plan/propose`），用 mock-agent 验证。
3. 批准与调度 + 黑板 `plan.md`。
4. TUI 审阅与进度界面。
5. 失败处理与重启恢复。

## 9. 待定问题

- 提议提示词的 JSON 约束对不同 Agent 的遵从度差异，是否需要为不擅长结构化输出的 Agent 提供降级方式？
- "任务完成"的判定仅靠"本轮结束"是否足够？是否需要任务级验收（运行测试命令）？
- 汇总由哪个会话生成，还是 daemon 仅做机械拼接？本期倾向后者。
