# agentmux TUI 多 Agent 新手体验优化计划

日期：2026-09-30
状态：P0、P1 和 P2 的非批量功能已实施，自动化回归通过；真实新用户验收待开展
范围：让新人能够在当前协作空间中发现、添加和切换多个 Agent

## 1. 目标与判断

当前 TUI 已具备在同一个工作区创建多个 Agent 会话的底层能力，但界面更像多个独立聊天窗口的管理器，没有把“在当前协作中加入一个 Agent”表达成清晰的操作。

新人找不到入口，主要是操作入口、术语层级和协作范围不明确，而不只是缺少快捷键或使用文档。

本计划优先解决从一个 Agent 到两个 Agent 的操作路径，保留现有对话主区与右侧栏，不进行整套布局重做。

## 2. 当前模型与能力边界

现有关系如下：

```text
Project：项目仓库
  Workspace：共享代码目录、Git worktree 和分支
    Session：Claude 的独立对话
    Session：Codex 的独立对话
    Session：Pi 的独立对话
```

- 一个 `Session` 只绑定一个 Agent profile；同一 `Workspace` 可以包含多个 `Session`。
- 同一个 Agent profile 可以创建多条独立会话，不能将 profile ID 当作成员实例 ID。
- 多个会话共享代码目录，但不自动共享完整聊天记录。
- 现有协作机制包括 `.agentmux/context.md`、`.agentmux/activity.md` 和手动跨会话引用。
- 添加 Agent 不代表自动分工，也不代表自动开始执行任务。
- 共享黑板不是文件锁，不保证多个 Agent 不会同时修改同一文件。

用户所说的“同一个会话开启多个 Agent”，本计划暂按“同一协作空间下的多个独立 Agent 对话”理解。

如果目标是多个 Agent 在同一个聊天流中轮流回答，需要另行设计消息路由、上下文共享和编排行为，不能只靠改入口名称实现。

## 3. 当前体验问题

| 问题 | 对新人的影响 | 源码依据 |
| --- | --- | --- |
| 主要入口叫 `+ New task`，没有当前空间的添加 Agent 入口 | 不知道新增的是另一项工作，还是当前工作的参与者 | `tui/src/shell.rs`：`draw_header` |
| 新建向导从项目开始，再选工作区和 Agent | 追加第二个 Agent 时仍需理解并重复选择容器关系 | `tui/src/app.rs`：`start_wizard`；`tui/src/newsession.rs` |
| Tasks、Agents、Workspace、New conversation 同时出现 | 任务、执行者、对话和容器的层级不稳定 | `tui/src/shell.rs`；`tui/src/ui.rs` |
| 工作区选择行主要展示名称 | 看不出空间已有成员，也不容易判断是否加入原有协作 | `tui/src/ui.rs`：`draw_wizard` |
| 工作区概览中的 Agent 数量和 active 数量来自所有会话 | 当前空间与全局范围混淆 | `tui/src/shell.rs`：`draw_sidebar` |
| 帮助主要说明新建任务和切换任务 | 未建立“给当前空间增加参与者”的操作路径 | `tui/src/shell.rs`：`draw_help` |

## 4. 建议的交互方向

### 4.1 明确区分两个动作

| 动作 | 用户意图 | 默认行为 |
| --- | --- | --- |
| 新建协作空间 | 开始另一件工作 | 选择项目、创建独立工作区，再选择首个 Agent |
| 添加 Agent | 为当前工作增加参与者 | 固定当前工作区，直接选择 Agent，创建独立对话 |

“协作空间”是用户侧候选名称，对应现有 `Workspace`，不是新增底层实体。最终文案需要确认；不要将现有所有 `task` 或 `session` 文案机械替换为同一个词。

保留加入其他已有工作区的能力，但将其作为明确的空间选择流程，不让新人承担追加 Agent 时重复选择项目和工作区的成本。

### 4.2 添加 Agent 的推荐路径

```text
正在和 Claude 讨论登录修复
  -> 添加 Agent
  -> 选择 Codex
  -> 确认加入 auth-fix
  -> 进入 Codex 对话
  -> 输入回归测试任务并发送
```

- 当前空间的 Agent 列表旁提供常驻添加入口。
- 窄屏时在顶部或切换器提供等价入口，不依赖侧栏展开或 slash 命令。
- Agent 选择界面展示目标空间名称与必要的分支信息，不再次询问项目和工作区。
- 没有当前空间时，引导进入新建或选择空间流程，不暗中选取列表中的第一个工作区。
- 完成添加后，在用户仍停留于该操作流程时进入新 Agent 对话；用户已切换到其他任务时，不让迟到响应抢走选择或草稿。
- 原有对话的草稿、引用、阅读位置和运行状态保持不变。

### 4.3 接收者与上下文

- 输入区始终明确当前消息的接收者。
- 默认只向选中的 Agent 发送，不默认广播。
- 新 Agent 使用独立聊天记录，不默认转发旧对话。
- 需要交接上下文时，由用户明确选择引用；已有共享黑板机制保持原有语义，不宣称完全没有共享信息。
- 同类 Agent 通过分工名称区分，例如“Codex · 回归测试”和“Codex · 代码审查”；列表和发送路由仍以 `session_id` 区分。
- 以真实成员、状态和引用来源表达协作关系，不用长篇常驻说明文字代替明确的控件和信息层级。

## 5. 分阶段实施计划

### 第一阶段：打通添加第二个 Agent 的路径

优先级：P0。目标是让已有会话中的用户直接进入当前工作区的 Agent 选择。

- [x] 增加当前协作空间的添加 Agent 入口，覆盖宽屏、窄屏、鼠标和键盘操作。
- [x] 将添加模式与完整新建模式区分，复用现有 Agent 选择与 `session/create` 能力。
- [x] 添加模式打开时固定目标 `workspace_id`，在确认界面显示对应空间；不随背景选择变化而改变目标。
- [x] 无当前空间时进入明确的新建或选择流程。
- [x] 保留完整新建流程，以及加入其他已有工作区的能力。
- [x] 提供创建中、连接中、可用和失败状态，避免将 RPC 成功返回等同于 Agent 已就绪。
- [x] 创建请求进行中防止重复提交；取消选择不影响已运行 Agent，提交后的关闭行为明确。
- [x] 创建或连接失败提供可操作的恢复入口，不静默产生重复成员。
- [x] 创建结果不覆盖原会话草稿，不让迟到响应抢走用户已切换的任务。
- [x] 无可用 Agent 时展示明确状态与配置入口信息，保留返回操作。
- [x] 补充状态机、渲染、消息路由和真实 PTY 回归测试。

建议涉及的模块：

- `tui/src/shell.rs`：入口、目标空间与状态呈现。
- `tui/src/newsession.rs`：新建与添加两种流程的状态。
- `tui/src/app.rs`、`tui/src/workbench.rs`：进入流程和空间上下文。
- `tui/src/ui.rs`、`tui/src/interaction.rs`：选择界面、命中区域和焦点。
- `tui/src/main.rs`：创建结果、失败处理与迟到响应行为。
- `tui/src/commands.rs`：如增加命令入口，处理 workbench 与 Agent 命令命名冲突。

原则上不新增领域实体、不修改现有 Session 与 Workspace 的关系、不先引入批量创建 API。具体文件范围在实施前根据最新代码确认。

### 第二阶段：让协作关系一眼可见

优先级：P1。目标是明确容器、成员、对话和任务分工的层级。

- [x] 确认并统一协作空间、Agent 对话、任务标题的用户侧命名。
- [x] 当前空间展示自己的成员数量和状态，另行标识全局统计范围。
- [x] 切换器区分当前空间的 Agent 与其他空间的对话。
- [x] 工作区选择列表展示已有成员或会话数量，帮助用户辨认目标空间。
- [x] 同类 Agent 的对话保持可区分，不依赖随机 ID 作为主要名称。
- [x] 保持输入接收者、列表选中项与实际发送路由一致。
- [x] 更新帮助与 README，使其与新的操作结构一致；文档作为补充，不作为唯一入口。

### 第三阶段：降低协作成本

优先级：P2。目标是在创建和切换已经清晰的基础上，降低分工与交接成本。

- [x] 提升“引用给另一个 Agent”的可发现性，保持先准备草稿、再由用户发送的行为。
- [x] 提供分工名称编辑；实施前确认标题与名称的持久化方式，避免将 Pi 自身的会话名称等同于通用 TUI 标题。
- [x] 展示共享文件活动与多人涉及同一文件的提示，不误称已发生冲突，也不误称已有文件锁。
- [x] 评估批量添加多个 Agent 的必要性；若实施，逐项呈现成功与失败，不让单项失败掩盖已创建成员。

批量添加评估结果：本轮暂不实施。单 Agent 追加已满足核心入门路径；批量请求的逐项恢复、部分成功和不确定提交结果应单独定义，不与本轮入口改造合并。

## 6. 本计划暂不包含

- 多个 Agent 共用一个完整聊天流。
- 自动任务拆解、自动选择 Agent 和自动分工。
- 默认广播用户消息或自动同步完整聊天记录。
- 默认在添加后立即执行任务。
- 自动解决共享代码修改冲突。
- 为本次入口优化重写整个 TUI 布局或底层编排系统。

上述能力如需推进，应分别确定行为契约和风险边界。

## 7. 验收标准

### 新人可用性验证

邀请几位未使用过项目的用户，不提供操作说明，观察能否完成以下任务：

- [ ] 从已有 Agent 对话中找到添加入口，并加入第二个 Agent。
- [ ] 正确确认第二个 Agent 加入的是当前空间，而不是另一个工作区。
- [ ] 理解两者共享代码目录，但聊天记录各自独立。
- [ ] 给第二个 Agent 发送任务，再切回第一个 Agent，草稿不丢失、消息不误投。
- [ ] 能够区分添加参与者与新建另一件工作的入口。
- [ ] 在窄屏下完成同样操作，不依赖 slash 命令或快捷键记忆。

记录首次发现入口的位置、重复选择次数、错误空间选择、接收者误判及是否需要口头解释。第一阶段验收重点是用户能否自然地从一个 Agent 走到两个。

### 工程回归验证

- [x] 使用同一个 workspace ID 创建第二条 Session，不额外创建 worktree。
- [x] 同一 Agent profile 可添加多个实例，分别使用不同 session ID。
- [x] 发送仅投递给选中的 Session；其他 Session 的运行不被中断。
- [x] 草稿、引用、阅读位置与待处理权限仍按 Session 隔离。
- [x] 覆盖取消、无可用 Agent、断线、创建失败、连接失败和重复确认。
- [x] 覆盖创建中切换任务以及迟到响应，保持用户当前选择和草稿。
- [x] 覆盖 80x24、120x30、160x40；更小窗口检查入口可达性、文字溢出和控件遮挡。
- [x] 用隔离 mock daemon 和 mock Agent 执行 PTY 回归，不重启或修改用户现有 daemon 与会话。
- [x] 执行 TUI 相关测试、格式检查与 Clippy；涉及共享逻辑时扩展对应回归范围。

## 8. 待确认项与建议顺序

- 用户最终目标是同一空间的多个独立 Agent 对话，还是同一聊天流中的多 Agent 回答。
- “协作空间”“添加 Agent”等最终界面名称，以及现有英文界面的文案对应关系。
- 第一阶段中，新建入口的文案调整幅度与当前完整向导的保留形式。
- 分工名称编辑与批量添加是否值得进入后续范围。

建议先确认第一项能力边界和第一阶段流程，再实施 P0。随后通过新人验证决定第二、第三阶段的具体范围，不一次性扩大为群聊或自动编排改造。

## 10. 实施记录

分支：`feat/tui-multi-agent-onboarding`。从用户现有工作区创建，保留此前未提交的改动，不进行清理或回退。

已开发的用户侧行为：

- 顶部、侧栏和切换器提供 `Add agent`，沿用当前空间直接选择 Agent。
- `New space` 默认选中新建工作区，仍可明确选择加入已有空间。
- 添加界面固定目标空间，显示名称与分支；请求进行中禁用重复确认，关闭后后台完成。
- 新建工作区后的会话创建失败可复用该工作区重试。
- Adapter 初始化失败时，`session/create` 返回已持久化的 Error 会话；通过 Resume 重试原记录，不隐藏失败成员。
- Agent 切换器优先显示当前空间，并支持粘贴名称搜索；输入区显示 `To:` 接收者。
- 当前空间与全局成员计数分开，同 profile 的默认名称使用空间内实例序号。
- Menu 中增加对话名称编辑。`session/title` 将 `TitleChanged` 事件持久化，历史返回 `title_seq`，防止迟到的历史响应覆盖新名称。
- 名称属于当前对话，Resume 或 daemon 重启形成的新对话边界会重置名称；Pi 原生 `/name` 仍保持独立语义。
- 侧栏增加 Quote 入口，文件活动显示已加载历史中观察到的多人涉及提示，不宣称完整审计、冲突或文件锁。

### 自动化验证结果

- `cargo build --workspace`：通过。
- `cargo test --workspace --quiet`：311 项通过，0 失败；3 项原有手动预览/性能测试忽略。其中 TUI 为 150 项通过。
- `cargo clippy --workspace --all-targets -- -D warnings`：通过。
- `cargo fmt --all -- --check` 与 `git diff --check`：通过。
- `tui/tests/multi_agent_pty.py`：40x16、80x24、120x30、160x40 全部通过，覆盖取消、当前空间添加、单次正确投递、原草稿恢复、中文命名、空间分组和重开。
- `tui/tests/close_panel_pty.py`：三种尺寸通过，覆盖鼠标输入突发、侧栏关闭与重开、中文发送、Resume & send、帮助、切换器、退出和终端模式恢复。
- `tui/tests/pi_commands_pty.py`：120/40 列命令控制、超过 1000 条 Unicode 增量恢复、1800 行思考与代码历史滚动全部通过；本次长历史测试最大滚动后输入延迟为 0.113 秒。

终端回归还发现并修复了两个边界问题：切换器没有处理名称粘贴；Ready 状态落盘先于尾部增量时，迟到字符可能被拆成另一条回复。后者通过事件时间区分迟到的本轮增量与正常的新回复，同时保留原有消息边界测试。

PTY 测试使用隔离目录内的 `pyte==0.8.2` 和 `wcwidth==0.2.13`，没有增加项目运行时依赖。Pi 回归脚本直接读取终端 buffer，避免 pyte 的 display helper 在空宽字符续格上抛出异常；完整正文、重复文本和延迟断言保持保留。

### 剩余边界

- 新人可用性验证仍需真实新用户参与，上方相应验收项保持未完成，不以自动化测试代替。
- 批量添加、默认广播、群聊和自动分工未纳入本轮。
- 文件活动来自当前已加载事件，不代表完整审计、独占归属、冲突检测或文件锁。
- 创建中退出 TUI 或网络断线导致响应未知时，现有 API 没有跨重连的创建幂等键。本轮防止 TUI 内重复确认，并显式保留已知连接失败的会话；未知提交结果需要重开后检查成员，不能宣称全局 exactly-once。
- 命名功能需要新版 daemon 与 TUI；本轮未重启用户实际 daemon。更新服务会断开运行中 Agent 的连接，应在可中断时操作，再按需要 Resume。
- 本轮没有 Git 提交或合并，用户原有未提交修改保留在当前实施分支的工作区中。
